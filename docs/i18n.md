# Internationalisation (i18n) Guide (Issue #1462)

StellarKraal targets East African users and ships with English (`en`) and
Kiswahili (`sw`) out of the box. This document explains the i18n architecture,
how translation strings are managed, and how to add a new locale.

## Architecture overview

The Next.js (App Router) frontend uses a lightweight custom i18n context
(`frontend/src/context/I18nContext.tsx`) instead of `next-i18next`. This was
chosen because App Router does not support the `getServerSideProps` pattern
that `next-i18next` relies on, and the custom context keeps the bundle small
with no extra dependencies.

Key moving parts:

| File / directory | Purpose |
|---|---|
| `frontend/src/context/I18nContext.tsx` | React context, `I18nProvider`, `useI18n()` hook, `t()` function |
| `frontend/public/locales/<locale>/common.json` | Translation strings for each locale |
| `frontend/scripts/validate-i18n.js` | CI script — fails if any English key is missing from another locale |
| `frontend/tests/e2e/i18n-language-switcher.spec.ts` | End-to-end test for the language-switcher UI |

### Locale detection and persistence

On first load, the app reads the user's locale preference from:

1. `localStorage` key `stellarkraal_locale` (primary — survives page reload).
2. Cookie `stellarkraal_locale` (secondary — available to server-side middleware).

If neither is set, `en` is used. The user can change language via the
`<LanguageSwitcher>` component in the navbar.

### Translation function

```tsx
import { useI18n } from "@/context/I18nContext";

function MyComponent() {
  const { t } = useI18n();
  return <h1>{t("dashboard.title")}</h1>;
}
```

`t("some.dotted.key")` resolves nested keys from the loaded JSON dictionary.
If a key is missing it returns the key string itself (safe fallback that is
visible and grepable). An optional second argument sets an explicit fallback:

```tsx
t("loans.emptyState", "No loans found")
```

## File structure

```
frontend/public/locales/
├── en/
│   └── common.json      ← source of truth; all keys live here
└── sw/
    └── common.json      ← Kiswahili translation; must contain every key from en/
```

Translation files are flat JSON at the top level but support arbitrary nesting.
The CI validation script (`validate-i18n.js`) rejects a PR if any English key
is absent from another locale file.

## Naming conventions

Translation keys follow a **namespace.section.identifier** pattern:

```
<page-or-feature>.<group>.<label>
```

Examples:

| Key | Usage |
|---|---|
| `nav.dashboard` | "Dashboard" label in the navbar |
| `wizard.stepCollateral` | Step title in the loan wizard |
| `loans.searchPlaceholder` | Placeholder text for the loan search input |
| `errors.networkError` | Generic network error message |

Rules:
- Use **camelCase** for each path segment.
- Keep keys as short as is unambiguous. `loans.noResults` is preferred over
  `loans.listPage.emptyStateNoResults`.
- Group all keys for a page under its route name (`dashboard`, `loans`,
  `collateral`, `transactions`, `settings`).
- Shared / cross-cutting strings live under `common` or a descriptive group
  (`errors`, `actions`, `units`).
- Never embed HTML markup in a translation value. Use separate keys for text
  that wraps a link or bold span, or use a render prop pattern.

## Adding a new locale

The following example adds Amharic (`am`).

### Step 1 — Copy the English file

```bash
cp frontend/public/locales/en/common.json frontend/public/locales/am/common.json
```

### Step 2 — Translate every value

Open `frontend/public/locales/am/common.json` and replace every English
string with its Amharic equivalent. Keep all keys unchanged — only the
values change.

```json
{
  "nav": {
    "dashboard": "ዳሽቦርድ",
    "loans":     "ብድሮች",
    ...
  }
}
```

### Step 3 — Register the locale in the context

Open `frontend/src/context/I18nContext.tsx` and add `"am"` to the
`SUPPORTED_LOCALES` array and the `Locale` type:

```ts
// Before
export type Locale = "en" | "sw";
export const SUPPORTED_LOCALES: Locale[] = ["en", "sw"];

// After
export type Locale = "en" | "sw" | "am";
export const SUPPORTED_LOCALES: Locale[] = ["en", "sw", "am"];
```

### Step 4 — Add the language-switcher label

Open `frontend/src/components/LanguageSwitcher.tsx` and add an entry for
Amharic so users can select it from the UI:

```tsx
const LOCALE_LABELS: Record<Locale, string> = {
  en: "English",
  sw: "Kiswahili",
  am: "አማርኛ",          // ← add this line
};
```

### Step 5 — Validate

```bash
cd frontend
node scripts/validate-i18n.js
```

The script exits with code `0` if every key in `en/common.json` is also
present in `am/common.json`. Fix any reported missing keys before opening
a PR.

### Step 6 — Run the e2e test

```bash
cd frontend
npx playwright test tests/e2e/i18n-language-switcher.spec.ts
```

## Requesting and reviewing community translations

1. **Open a translation issue** using the label `i18n` and title format
   `Add <LocaleName> (xx) translation`. Describe the target audience and link
   to the existing `en/common.json` as the source file.

2. **Assign a reviewer** who is a fluent speaker of the target language. At
   least one reviewer must have native or near-native proficiency; machine
   translations are accepted as a starting point but must be reviewed before
   merge.

3. **Submit as a PR** that follows the steps above. The CI `validate-i18n.js`
   script will confirm key coverage automatically.

4. **Review checklist:**
   - [ ] All keys from `en/common.json` are present.
   - [ ] Values are natural-sounding translations, not word-for-word
         machine output.
   - [ ] Domain-specific terms (loan, collateral, XLM, stroops) are
         consistently translated or intentionally left in English where no
         natural equivalent exists.
   - [ ] The UI renders correctly with the new locale (run the e2e test).
   - [ ] Right-to-left locales (Arabic, Hebrew) are tagged with `dir="rtl"`
         — see the RTL support issue (#1524) for guidance.

## CI integration

The `frontend-ci.yml` workflow runs `node scripts/validate-i18n.js` as part
of the lint job. A PR that introduces new English keys without updating all
other locale files will fail CI.

To add new keys to an existing locale incrementally (e.g. a large page is
being translated by a community volunteer), temporarily add the missing keys
with an empty string `""` as a placeholder. The validator treats empty strings
as present; a separate PR can fill them in.
